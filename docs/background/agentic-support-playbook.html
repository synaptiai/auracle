The build

What sits behind each box on the wall. Detail diagrams here are backup, not slides. Draw them only when someone asks.

Front door

Agent owns
  • One entry point across chat, email, in-app widget and API. Enrich with plan, workspace, account state and recent product events before anything is classified.
  • Classification produces three things at once: type, urgency and confidence. Type decides the destination. Confidence decides who handles it.
  • Above 85, auto-route and resolve. Between 60 and 85, the agent drafts and a human approves. Below 60, manual triage with the enrichment already attached.
  • Bug, feature request and usage confusion go to different systems. Bugs carry structured fields into the issue tracker. Feature requests go to the feedback store, never the ticket queue.
WhyTriage before the queue removes the back-and-forth. Tagging and routing is the highest-return first move because it improves throughput without taking risky actions.

Knowledge layer

Shared
  • One hub: docs, FAQs, troubleshooting flows, release notes, public changelog. This is the grounding source for every agent.
  • Structure content around intents, not features. "Why is my workspace locked" is a page. Target a 90-second self-solve.
  • Every agent answer cites the article or snippet it came from, so answers can be audited and corrected.
WhyGrounded answers are correctable. Ungrounded answers are not. This is also the box teams skip, and it is the one that determines whether the rest works.

Autonomous resolution

Agent owns
  • Start with password resets, account access checks, and subscription or plan status, wired to auth and billing.
  • Deterministic flows for onboarding questions: inviting teammates, connecting a provider, first workflow run.
  • Fire automation off product events. An error code or rate-limit trigger either fixes the issue or offers a one-click fix.
WhyHigh volume and low complexity first. Containment in the 60 to 70 percent range is reachable on this class of ticket without moving CSAT.

In-product support

Agent owns
  • Embed the agent where the work happens, with access to the current page, recent actions and workspace configuration.
  • Side panel on complex flows: explain the error, propose the fix, or open a ticket that is already filled in.
  • Behaviour triggers. Three failed retries on the same action offers help before the user files anything.
WhyA ticket that is never filed costs nothing to resolve. Catching friction at the point of failure beats catching it after churn risk appears.

Noise and signal

Shared
  • Feedback intake is a separate flow from incident support. Structured fields: workflow affected, frequency, business impact.
  • Cluster into themes and merge duplicates automatically. Product sees trends, not raw volume.
  • Changelog entries reference the intents they close. Tell people when their report shipped.
WhyTreating all feedback as equal buries the signal. Closing the loop out loud is what makes people willing to use self-service next time.

Proactive education

Human owns
  • Effort-score micro-surveys at defined moments: first automation run, first cowork session, first integration.
  • Playbooks for the common jobs to be done. Support reuses them as the canonical answer rather than writing prose each time.
  • Surface recorded sessions automatically when a ticket matches the topic.
WhyShort surveys at the moment of friction produce better data than long ones sent a week later.

Escalation design

Shared
  • Policy per intent, not per channel. The matrix below is the whole policy. Every intent gets a risk tier, and the tier plus the confidence band determines who acts.
  • Hard triggers override the matrix regardless of confidence: negative sentiment, phrases like cancel or security, high-value accounts, and multi-channel contact inside a short window.
  • Nothing crosses the boundary empty-handed. The handoff payload is a contract, not a courtesy.

Metrics

Shared
  • Containment rate, escalation frequency, fallback rate, re-open rate, and CSAT split by automated versus human resolution.
  • Standard events at intake, classification, action, escalation and resolution, so flows can be traced and tested against each other.
  • Weekly review of automation errors, top intents by volume, and near misses where automation almost resolved the case.
WhyNear misses are the cheapest source of the next automation. They tell you exactly which threshold to move.

Architecture

Shared
  • Five agents with narrow jobs: intake, answer, workflow, feedback, escalation. Each reads and writes the same schema.
  • The schema is the contract. Ticket is the spine. Intent carries the risk tier and policy, which is what makes the escalation matrix executable rather than a document.
  • Vector-backed knowledge layer with a named owner per source. If nobody owns docs, tickets and telemetry, this is a staffing problem, not an architecture problem.

Build order

Phased
PHASE 1

Audit and triage

  • Tag three to four weeks of interactions by intent, volume, handle time and repeat rate. Rank the top 10 to 20 by return.
  • Define the support schema. Ship intake and triage with confidence bands and basic routing.
PHASE 2

Self-service and volume

  • Stand up the knowledge layer and connect it to the answer agent with retrieval grounding.
  • Automate password and account flows end to end. Launch in-product support on the most complex workflow you have.
PHASE 3

Feedback loops

  • Split feedback intake from incident support. Add clustering and deduplication.
  • Wire changes into a changelog that references the intents it closes. Instrument onboarding with effort scores.
PHASE 4

Higher-risk automation

  • Add workflows with real side effects, governed by per-intent risk policy, idempotency keys and audit logs.
  • Feed closed tickets back into intent models. Auto-propose knowledge updates where automation struggled.

Running the session

Facilitator

Expect the argument about which tickets get automated

Do not let the room have it by topic. The lifecycle diagram exists to show that the split is by confidence and risk. Redraw the two thresholds live if people push. That is the productive version of the argument. If they push further, put up the policy matrix.

Ask who owns each knowledge source

Point at the knowledge layer box and read the list out loud. Docs, tickets, telemetry, CRM, release notes. If nobody names an owner for each, stop and fix that before discussing agents.

Name the return arrow

Most support automation quietly fails at the loop diagram, not the system map. Volume drops, everyone declares victory, and the signal never reaches the roadmap. Leave the session with a person attached to that arrow.

Close on two numbers

The starting confidence thresholds and the first three intents to automate. Everything else in this pack can be decided later.
