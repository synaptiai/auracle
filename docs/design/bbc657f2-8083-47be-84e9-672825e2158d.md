# V2 Design: Online A/B Experiments

Status: proposed, blocked (card 25761e26). Traces to section 1.2 and section
4.10 of `docs/v1-architecture.md`. This document changes no DEC and no code. It
records a proposal a person can adopt, amend or reject.

---

## 1. The problem

Section 1.2 excludes online A/B tests from V1. Section 4.10 states the reason.
To find a 5 percent change in containment you need approximately 470 cases. To
find a 2 percent change you need approximately 3 000 cases. Test-bed volume
cannot supply these numbers online.

Three gates block this feature today. Each gate has a different owner.

- **B1: no volume.** The repository ships synthetic fixtures only (DEC-18). No
  live Phase 2 deployment runs. `bands.yaml` keeps every baseline null. An
  experiment that starts below the sample size in section 4.10 produces noise.
- **B2: no decision.** The axis to vary is a person's decision. The schema for
  arm assignment needs ratification. Nothing in the register authorises either.
- **B3: replay cannot arbitrate.** Section 4.10 states that replay scores a
  history the system did not change. A prompt change alters the path. Only an
  online comparison of two arms measures the difference. This is why the
  feature exists at all.

## 2. Experiment axes

A person ratifies the axis for each experiment. The system does not choose. The
register constrains what a person can choose without an amendment.

| Axis | Varies | Register interaction | Position |
|---|---|---|---|
| A1 Prompt version | Composer and classifier prompt text | DEC-26 already pins and journals `prompt_ver` per run | **Recommended first** |
| A2 Gate thresholds | Agreement gate; groundedness 0.70 block and 0.80 review | DEC-07 pins the groundedness values in code. DEC-13 sets one person-owned global threshold | Not first. Needs a register amendment |
| A3 Retrieval config | RRF candidate depth; rerank depth | DEC-21 fixes the reranker on and 50 as the candidate floor | Second |

**Recommendation, A1 first.** Both arms of a prompt experiment run identical
gates, identical thresholds and identical retrieval. The comparison isolates
one cause. `run.prompt_ver` and `run.model_ver` already journal the inputs
(DEC-26). No DEC moves.

A2 changes the gates themselves. The values 0.70 and 0.80 live in
`src/policy/policy.ts` and trace to DEC-07. Varying them online weakens the
block and review rules for one arm of the tickets. A person must amend the
register before this axis runs. This document does not propose that amendment.

A3 changes what groundedness can cite. Coverage measures claims against
retrieved text (DEC-07). A retrieval change moves the evidence base under both
gates. It is a sound second experiment, not a first one.

**Person-owned decision.** The axis, the arm values, the salt and the minimum
detectable effect are set by a person for each experiment. This mirrors DEC-13:
a person sets a threshold, the system does not learn one.

## 3. Assignment mechanism

### 3.1 The key

The arm derives from the partition key, not from the run.

```
arm = uint64_be(SHA-256(experiment_salt + ':' + partition_key)[0..8]) mod k
```

- The `partition_key` is the DEC-27 key. Today it is `ticket_id`
  (`partitionOf` in `src/coordinator/coordinator.ts`). If the multi-turn
  proposal (design doc 8bd63fe0, draft DEC-35) is ratified, the key becomes
  `conversation_id ?? ticket_id`. Assignment follows the same expression.
  Every turn of one conversation then sits in one arm.
- The `experiment_salt` is a random value fixed when the person creates the
  experiment. It differs per experiment. Two experiments on the same tickets
  then produce uncorrelated arms.
- `k` is the arm count. The seed is `k = 2`: one control arm and one treatment
  arm.

### 3.2 Stability rules

1. Assignment is stable per ticket. It holds across runs and across turns.
2. The key never derives from `run_id`, from a message id, or from a timestamp.
   Two runs of one ticket produce one arm. This mirrors DEC-24: the idempotency
   key comes from action semantics, never from run identity. The assignment key
   comes from the ticket, never from the run.
3. Assignment is journaled on each run. Replay and offline analysis reconstruct
   arm membership from the ledger alone.
4. Integrity is an assertion, not a comment. The coordinator re-derives the arm
   from the key and compares it to the journaled arm. A mismatch sends the run
   to `escalated`. The temperature assertion in section 4.5 sets this pattern.

### 3.3 Schema implication, proposed only

Proposal for ratification. This card creates no file under `db/`.

```sql
ALTER TABLE run ADD COLUMN IF NOT EXISTS experiment_id text;
ALTER TABLE run ADD COLUMN IF NOT EXISTS arm text;
CREATE INDEX IF NOT EXISTS run_experiment_idx ON run (experiment_id, arm);
COMMENT ON COLUMN run.experiment_id IS 'Active experiment. Null outside an experiment.';
COMMENT ON COLUMN run.arm IS 'Assignment arm derived from the partition key (draft DEC-39). Null when experiment_id is null.';
```

Alternative: a separate table keyed by `(experiment_id, partition_key)`. That
table centralises the assignment. It also needs a join for every analysis, and
it duplicates what a deterministic hash gives for free. The run columns win.
Both arms of one experiment share one ledger, one partition layout and one set
of gates. The axis under test is the only difference.

## 4. Viability gate

Activation criteria, in the style of design doc 899a1565. A person sets the
final numbers. The seed values follow the sensitivity math in section 4.10. No
experiment starts until every criterion holds.

- **E1 Volume floor.** The trailing window holds at least 470 disposition
  bearing cases per experiment for an MDE of 5 points. It holds at least
  3 000 for an MDE of 2 points. Below these numbers the experiment does not
  start. Section 4.10 gives the arithmetic.
- **E2 Pre-registration.** The person declares the axis, the arms, the salt,
  the MDE, the alpha and the window before the first ticket is assigned.
  Nothing is tightened after data arrives.
- **E3 Freeze.** No threshold, calibration or DEC value changes inside the
  window. Each arm pins its prompt and model versions (DEC-26).
- **E4 Per-arm gate floors.** Sample agreement and groundedness coverage hold
  in each arm separately. An arm that breaches a floor stops the experiment,
  not just the arm.
- **E5 Assignment audit.** Before any readout: the arm split is balanced, and
  every journaled arm equals the re-derived arm (section 3.2, rule 4).
- **E6 Blast-radius cap.** A daily cap bounds the treatment arm's automatic
  actions. DEC-25 sets the philosophy: a limit makes damage visible, not a
  surprise.
- **E7 Reversion.** One config value ends the experiment. Every new ticket
  returns to the control configuration. Reverting needs no code change.
- **E8 Person approval.** The person who owns the axis decision also owns the
  start decision. Both are recorded, as DEC-13 records a threshold.

## 5. Measurement plan

**Primary metric: containment.** It derives from observable dispositions
(DEC-32). Per arm: the share of runs that end `resolved` on the automatic path,
against the share that end `escalated`. The policy decision scores against the
observed disposition. It never scores against an intent label. Intent labels
come from the induction job, which is a component under test.

**Secondary metric: approval-edit distance.** Section 4.10 names it the online
measurement. It needs no labels and no counterfactual. Report the median and
the ninetieth percentile per arm. The measurement is blind to confident errors,
in the way paragraph 3.2 describes. It supports the readout. It does not carry
it.

**Gate independence.** Sample agreement and groundedness coverage stay two
independent gates (DEC-05). Each is reported per arm, as its own number. No
composite score blends them. This rule binds the analysis, not only the
runtime.

**Analysis.** A two-proportion comparison on containment between arms. Wilson
intervals per arm; the calibration and gold-report jobs already carry Wilson
code. Under the multi-turn proposal (draft DEC-38), first turns score by
replay and later turns score online only. An online experiment covers both,
because assignment holds per conversation.

**What a readout cannot show.** An A/B measures the system under two
configurations. It does not attribute a regression to a component. The journal
and the pinned versions (DEC-26) supply attribution after the readout.

## 6. Non-goals

- No code in this card. No file under `db/`. The migration in section 3.3 is a
  proposal.
- V1 behaviour is unchanged. The control arm is exactly V1.
- No per-intent thresholds. DEC-13 rejects them. Paragraph 3.3 puts the data
  cost near 8 000 labelled tickets per threshold.
- No gate experiments (axis A2) until a person amends the register.
- No more than two arms in the first experiments. More arms divide the volume
  that E1 already strains.

## 7. Draft decisions for the register

Numbering assumes the multi-turn drafts (DEC-34 to DEC-38, design doc
8bd63fe0) are ratified first. The person assigns the final numbers.

| ID | Decision | Rejected alternatives |
|----|----------|----------------------|
| DEC-39 | A run's arm derives from a deterministic hash of the partition key and an experiment salt. Assignment is journaled per run | Random assignment; assignment from run id; assignment from arrival order |
| DEC-40 | An experiment starts only when sustained volume supports its declared MDE. Both gates hold in every arm. No score blends them | Start now, stop on pain; a combined confidence score |

**DEC-39.** Assignment follows the ticket, not the run. The same ticket gives
the same arm across every run and every turn. This is the DEC-24 principle
applied to experiments: identity comes from semantics, never from the run.
Random assignment loses the audit trail. Run identity breaks stability across
retries. Arrival order couples the arm to deployment timing.

**DEC-40.** Section 4.10 sets the price of a signal. An experiment that starts
under-powered ends in noise or in a mid-flight extension, and an extension is a
design change. The gate floors keep every arm inside the safety envelope that
DEC-05 and DEC-07 define. Blending the two gates into one score hides a
confident error, as paragraph 3.2 shows.
