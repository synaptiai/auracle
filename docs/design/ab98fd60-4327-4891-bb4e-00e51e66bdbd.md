# Decision trace: bounded intra-partition concurrency needs no new decision

Status: a trace, not a proposal. It answers one question the item 7 design
document left open. That document is
`99dc14d7-da9d-4a92-a9dc-d7c0685c6992.md`.

The maintainer confirmed the trace on 2026-09-04. No row enters section 2, and
section 7.1 records the same conclusion.

## The question

The item 7 document maps five corrections for head-of-line delay. Option 1 is
bounded intra-partition concurrency. The document says this about it: whether
option 1 needs a register note is an open question, not a settled one.

This trace answers it. The answer is no. The correction is an implementation
detail of DEC-27, and it needs no row in section 2.

## Why no decision changes

DEC-27's row names the ticket id as the key, and one consumer for each
partition. DEC-36 later replaced that key with the conversation id. The
rejected alternative of DEC-27 is a lease with a lock service.

The row constrains ownership. It says how many consumers own a partition. It
says nothing about how many tickets one consumer works at once. The item 7
document states the same reading, and it places all five options inside it.

DEC-36 moved the partition key to the conversation id. Runs on one
conversation therefore land in one partition, and the serialization the
partitions exist for is per conversation. Concurrency across different
conversations breaks nothing that decision protects.

DEC-25 limits the cost, the steps and the clock time. The concurrency bound
belongs with those limits, because a bound makes damage visible. So the
bound is pinned in code and it is not left as guidance.

Precedent supports the conclusion. V2 open item 6 closed with no decision at
all. Section 7.1 records it as closed by `../../src/ledger/migrate.ts`.

## What the correction must prove again

`../../src/coordinator/consumer.ts` carries a proof at its head. It shows
that a rebalance overlap cannot double-process a ticket. That proof assumes
the scan walks its batch serially, and this correction removes that
assumption.

Three things must be re-derived rather than inherited.

**One ticket, two queued messages.** `pollPartition` keys on the message, and
the code says so at the ack: a ticket may hold several queued messages. A
parallel walk could then run two rows of one ticket at once. The item 7
document gives the remedy: group the poll by ticket, and serialize the rows
of one ticket inside the scan.

**The epoch read.** `nextEpoch` reads `ticket_epoch` and then plans one above
it. That read and that write were safe while one run happened at a time. Two
concurrent runs on one ticket would read the same fence. Grouping by ticket
removes the case that produces it.

**The rebalance branch.** The old proof argues that an old run either loses
to the new owner or finishes and acks first. With K tickets in flight the
second branch no longer covers the tickets behind the one that finished.
`../../src/ledger/concurrency.db.test.ts` pins the serialized-writer
semantics, so read it before changing the walk.

The correction therefore ships with a new database test. It seeds two queued
messages of one ticket in one scan, and it proves they do not overlap.

## The evidence gate

The item 7 document rejects one alternative by name: ship option 1 now. Its
reason is that the option multiplies the blast radius of every scan before
any evidence says the tail causes the wait.

That rejection stands, and this epic clears it rather than ignoring it. The
document gives rule R3: apply option 1 when depth is uniform and a few long
runs cause most of the wait. `pnpm run latency` reports the percentiles that
decide R3.

So the order is fixed. The traffic seeder runs first. The latency report
reads the result. Option 1 lands only when R3 holds, and the change set
records the percentiles that showed it.

## Rejected alternatives

- **Add a decision for the bound.** DEC-25 already limits cost, steps and
  clock time. A second row for one more bound adds a citation and no rule.
- **Raise the partition count instead.** This dilutes the delay and removes
  none of it. It also grows the rebalance overlap the fence must cover.
- **Shed slow runs to a side queue.** This changes which runs finish and
  when, so it is a visible behaviour change and needs its own trace.
- **Ship the correction before the measurement.** The item 7 document
  rejects this by name, and the register's method runs the measurement first.

## Open items

None. The maintainer confirms the trace, and the correction proceeds as an
implementation detail once R3 holds.
