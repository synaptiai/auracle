# V2 Design: Per-Intent Agreement Thresholds

Design proposal for V2 open item 5 and section 1.2 of `docs/v1-architecture.md`.
Status: blocked on the trigger. The mechanism is specified here. No code lands
with this document. Nothing here is a decision until the lead ratifies it into
the register. The document obeys Simplified Technical English.

## Verdict

DEC-13 blocks the code today. It selects one global agreement threshold. It
rejects "a threshold that the system learns for each intent". The policy engine
enforces that threshold in `src/policy/policy.ts`. A change there needs a
register decision first. The register holds no decision that permits a
per-intent threshold.

The trigger cannot fire in this repository. Open item 5 asks for approximately
8,000 labelled tickets. The shipped gold set holds 770 synthetic cases (DEC-31,
DEC-18). The calibration job pins the fit half at exactly 385. The feedback
clusters card landed code because its volume trigger fires on synthetic data.
This trigger never does.

This card therefore delivers what the auto-replies card delivered: the design,
the candidate decision, and the mechanism for the day the data exists.

## Why DEC-13 exists

Section 3.3 gives the evidence. One global threshold needs 385 labelled tickets
for an interval of 5 percent. A threshold for each of 25 intents needs
approximately 2,400 tickets. Intent frequencies follow a Zipf distribution. The
intent at rank 20 therefore needs a corpus of approximately 7,700 tickets. Open
item 5 rounds this to 8,000.

Rare intents never collect enough cases at test-bed volume. A threshold fitted
on thin data gives an appearance of accuracy and nothing more. DEC-13 is the V1
answer to that result. The V2 question is whether the data position changed,
not whether the math changed.

## The trigger

The trigger counts person-labelled gold cases, both halves. DEC-02 states that
the history has no tags. People label the cases. Section 5 calls this labelling
the largest single cost in the plan. The corpus export job gives the raw
threads. It labels nothing.

The check is code, not guidance. It behaves like `MIN_MONTHLY_FEEDBACK_EVENTS`
in the feedback clusters job:

- Below 8,000 labelled cases, the calibration job fits the global threshold
  only and writes `per_intent: {}`. Every intent keeps the global threshold.
- At or above 8,000, the job fits per-intent thresholds for intents above the
  data floor.
- The artifact records `trigger_min_labelled` and `labelled_cases`, so a
  reader can audit the refusal.
- A person adjusts the seed the same way as `GATE_AGREEMENT` (DEC-13).

The check operates on each calibration run. Section 4.11 gives the monthly
cadence. Each run mints a new artifact version, so per-intent values refresh
with the data.

## The data floor and the fallback

The floor comes from the section 3.3 arithmetic: 2,400 tickets across 25
intents is approximately 96 fit tickets per intent.

- An intent with at least 96 fit-half samples gets its own threshold and its
  own Wilson interval.
- An intent below the floor reads the global threshold. This includes `other`
  (DEC-10) and every Zipf-rare intent. The fallback is the card requirement:
  the global threshold stays in force wherever the data cannot support a fit.
- The floor is a person-set seed, like `GATE_AGREEMENT`.

The fit groups samples by the intent the threshold will gate. That intent is
the modal intent of the run, not the gold label. The runtime gate asks whether
the samples agreed on the intent the system chose. The fit population must
match the runtime population.

The interval cost is plain. At 96 samples the Wilson interval is approximately
10 points wide at p = 0.5. The global interval at 385 samples is 5 points. Each
per-intent number publishes with a wider bracket. The artifact carries the
interval beside each threshold, so no reader mistakes the precision.

## The mechanism when it starts

Three surfaces change: the calibration job, the artifact, and the policy path.

### Calibration job

- The samples gain the modal intent id. `classifyTicket` already returns it.
- The job groups fit-half samples by modal intent. Each group at or above the
  floor goes through `fitAgreementThreshold` unchanged: same precision floor,
  same selection rule, same Wilson interval.
- An intent above the floor with no threshold that reaches the target precision
  is recorded under `unfittable`, not dropped. It reads the global threshold.
  The global fit must still succeed on the same data, so the run never ends
  with no gate at all.
- The synthetic assertions stay. Source `synthetic` and exactly 385 fit tickets
  (DEC-31). An adopter gold half declares its own source and count. DEC-18
  still forbids shipping it. The adopter loader keeps the DEC-31 discipline:
  disjoint halves, fit and report.

### Artifact

The current fields stay. Five fields join them: `labelled_cases`,
`trigger_min_labelled`, `data_floor`, `per_intent` and `unfittable`.

The example shows a post-trigger artifact from an adopter deployment. An
adopter gold half declares its own source, so `gold_source` is never
`synthetic` here. The values are illustrative.

```json
{
  "artifact": "agreement-threshold",
  "version": 9,
  "fitted_at": "2027-01-05T09:00:00Z",
  "gold_source": "adopter",
  "split_used": "fit",
  "fit_tickets": 4000,
  "labelled_cases": 8000,
  "trigger_min_labelled": 8000,
  "prompt_ver": "classify-p1",
  "model_ver": "…",
  "target_precision": 0.985,
  "threshold": 0.6,
  "precision_at_threshold": 0.99,
  "coverage_at_threshold": 0.74,
  "interval": { "confidence": 0.95, "lower": 0.98, "upper": 0.997 },
  "data_floor": 96,
  "per_intent": {
    "billing_refund": {
      "fit_tickets": 214,
      "threshold": 0.55,
      "precision_at_threshold": 0.99,
      "coverage_at_threshold": 0.81,
      "interval": { "confidence": 0.95, "lower": 0.96, "upper": 0.997 }
    }
  },
  "unfittable": ["account_merge"]

```

- `labelled_cases` counts both halves. `fit_tickets` counts the fit half
  alone. The trigger reads `labelled_cases` against `trigger_min_labelled`.
- The shipped repository produces a different artifact: `gold_source`
  `synthetic`, `fit_tickets` 385, `labelled_cases` 770 and an empty
  `per_intent` map.
- An empty `per_intent` map is valid. It means the trigger checked and
  declined.
- Validation whitelists each entry's keys, mirroring the triage artifact. An
  added key fails the load instead of riding along.
- Each entry interval must bracket its precision, as the global interval must.
- The report half keeps its role. Each published per-intent number comes from
  report-half cases (DEC-31), never from the cases that fitted it.

### Policy engine and coordinator

- `PolicyInput` gains an optional `agreementThreshold`. The engine compares
  agreement against it and defaults to `GATE_AGREEMENT`. The engine stays pure.
  It reads no artifact and no state. The caller resolves the value.
- The resolution order is `per_intent[modal intent]`, then the artifact
  threshold, then the `GATE_AGREEMENT` seed.
- The coordinator loads the highest artifact at startup and resolves the value
  per run, next to the classification it already holds.
- This closes a V1 gap. Today no runtime component loads the artifact. The
  engine reads the seed constant, and calibration output is an audit trail.
  The wiring makes both the global refit and the per-intent values take
  effect.
- The rule order does not move. Idempotency capability (DEC-06), customer
  visibility (DEC-12), irreversibility (DEC-03), high risk tier (DEC-13), then
  gate 1. A high-risk intent gates before any threshold is read.
- The gold report job records the threshold in force for each case, in place of
  the seed constant it records today.

## Gate independence

DEC-05 holds. Only the cutoff of gate 1 varies by intent. Both gates still
report their own result. No code blends agreement with coverage. The
groundedness thresholds stay 0.70 and 0.80 for every intent. No DEC permits a
per-intent groundedness value, and open item 5 does not ask for one. The
classifier temperature assertion stays untouched (section 4.5).

## Proposed decision

| ID | Decision | Rejected alternatives |
|----|----------|----------------------|
| DEC-39 | Above a person-set data floor, the agreement threshold is per-intent. Below the floor, one global threshold applies | Per-intent thresholds with no floor; per-intent groundedness; learned risk tiers |

The floor is the whole decision. DEC-13 rejected per-intent thresholds because
rare intents never collect enough cases (section 3.3). A floor plus a global
fallback keeps that protection. An intent earns its own threshold only when its
interval can carry it.

The first clause of DEC-13 survives unchanged. A person still sets each risk
tier, and the system never learns a tier. A per-intent threshold refines gate 1
only. The `other` group and each rare intent stay on the global threshold.

## Rejected alternatives

- **Fit per-intent thresholds on the synthetic fixtures now.** Each intent
  holds approximately 15 fit tickets. That is the appearance of accuracy
  section 3.3 rejects. The code path would stay dead in every shipped run.
- **Land the policy change behind a flag now.** The register governs V1. The
  multi-turn card set the pattern: candidate decisions land as a design, and
  code follows the ratified register.
- **Per-intent groundedness thresholds.** No DEC permits them. Section 4.7
  fixes 0.70 and 0.80.
- **Group the fit by gold intent.** The runtime gate scores runs by modal
  intent. The fit population must match.
- **Learn the risk tiers with the thresholds.** DEC-13 assigns tiers to a
  person. The two compose: the tier gates first, the threshold second.

## Schedule when the trigger fires

1. Ratify DEC-39 into the register.
2. Label the gold set to 8,000 cases. This is person-owned work and the
   largest single cost (section 5).
3. Generalize the gold loader past the synthetic pins. Keep the split
   discipline.
4. Extend `calibrate.ts`, `run.ts` and `artifact.ts` with the trigger, the
   floor and the per-intent map.
5. Add the policy input, wire the coordinator artifact load, and record the
   threshold in force in the gold report.
6. Add evals: trigger refusal, floor fallback, per-intent interval brackets,
   gate independence.
7. Run build, tests and lint. Paste each output.
