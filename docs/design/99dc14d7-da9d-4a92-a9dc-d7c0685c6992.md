# V2 Design: Head-of-Line Delay Correction

Status: proposed (card db639d23). Traces to section 6, DEC-27, DEC-28 and
open item 7 of `docs/v1-architecture.md`. This document changes no decision.
It lands one measurement as an implementation detail. The document obeys
Simplified Technical English.

## Verdict

No correction can be chosen today. The choice depends on the shape of the
production latency distribution. The repository ships synthetic fixtures only
(DEC-18), and no Phase 2 deployment runs. Each option in the design space
fails in a different way. Picking one without data trades a known failure for
an unknown one. Section 6 states the same exchange for partitions themselves.

This document does three things. It maps the design space with each option's
cost. It lands the columns that make Phase 2 latency data collectible. It
fixes decision rules that read that data.

## The problem in the code

The delay has three sources, all visible in `src/coordinator`.

1. The poll reads oldest first. `pollPartition` orders by `enqueued_at`, so
   tickets leave the queue in arrival order (db/004, `intake`).
2. The consumer walks its batch serially. `processQueuedTickets` awaits each
   `coordinateTicket` before the next. One slow run holds every ticket behind
   it. A run makes several model calls: nine classifier samples, one
   embedding, one composition, one groundedness check.
3. The loop sleeps `intervalMs` between scans. A ticket that misses a scan
   waits one full interval extra.

Section 6 states the limit plainly. Partitions remove concurrent runs on one
ticket. They add head-of-line delay in each partition. V1 does not correct it.

## What the register fixes, and what it leaves

DEC-27 gives exclusive access through ownership, not through locks. Its
rejected alternative was a lease with a lock service (section 3.4). The
guarantee is per ticket: two runs on one ticket cannot occur together in
normal operation.

The guarantee says nothing about partition throughput. Nothing in DEC-27
fixes the order of tickets inside a partition. Nothing limits how long one
run blocks the next. DEC-28 covers only the ownership overlap of a
rebalance. The register leaves the delay alone and says so in section 6.

One boundary matters for the design space. DEC-27 constrains ownership: one
consumer per partition. It does not constrain how many tickets that consumer
works at once. All options below stay inside this reading. Whether option 1
needs a register note is an open question, not a settled one.

## The design space

Each option lists its mechanism, its interaction with DEC-27 and DEC-28, its
cost, and the data pattern that would justify it.

### 1. Bounded intra-partition concurrency

The consumer works up to K tickets of its partition at once. The scan becomes
a bounded parallel walk instead of a serial loop.

The per-ticket guarantee survives. Intake holds one row per ticket today, so
one poll never returns a ticket twice. Scans never overlap. Each ticket keeps
exactly one run. DEC-27's text stays true: one consumer still owns the
partition.

The cost grows with K. Peak model spend per scan multiplies. A crashed scan
aborts K runs instead of one. Per-ticket error isolation stays, because each
walk keeps its own try block. The concurrency bound K needs a limit pinned
like any other (DEC-25 spirit: a bound makes damage visible).

One V2 interaction needs care. The multi-turn proposal (DEC-35, design id
8bd63fe0) changes the intake key to `(ticket_id, message_id)`. A poll can
then return two rows of one ticket. The scheduler must serialize rows of one
ticket inside the scan. Grouping the poll by ticket is enough.

Data pattern: uniform depth across partitions, with a heavy tail in service
time. Concurrency removes the blocking; reordering cannot.

### 2. Priority ordering within a partition

Replace arrival order with a priority expression in the poll.

The ledger holds no priority signal today. A priority column would have to
join the intake table, and the adopter would have to feed it. Reordering
helps only the prioritized class. It moves delay onto the other tickets; it
removes nothing. Aging terms guard against starvation of the low class.

Priority by age alone is the current behaviour. FIFO is priority with every
weight at zero.

Data pattern: one class bears disproportionate harm from wait, such as a
contractual response time. No other pattern justifies it.

### 3. Work stealing between partitions

An idle consumer polls a partition it does not own and works the oldest
ticket there.

A steal is a mini-rebalance, and the register already owns that shape. The
stealer bumps the fence of the stolen ticket first, in one transaction. This
is the `claimPartition` mechanism at ticket granularity instead of partition
granularity. DEC-28 keeps safety: the old owner's next write fails as
`stale_epoch`. The existing consumer rule gives liveness: a refused ticket
stays queued, and the stealer picks it up on its next scan.

During a steal, two consumers briefly share one partition. That is the same
overlap a deployment rebalance produces. The fence covers it, not the
ownership rule. The letter of DEC-27 bends for the duration of each steal.

The cost is decision load. A consumer must read foreign queue depth to know
when to steal. Steal thrash needs a threshold and a backoff.

Data pattern: skew. A few deep partitions sit beside idle ones.

### 4. Dynamic partition count

Raise N when load grows, without a deployment.

The current hash is plain modulo. Changing N remaps every ticket, which is a
full rebalance with epoch churn everywhere. Consistent hashing reduces the
movement. It changes only the hash function, which is an implementation
detail, but it moves tickets mid-flight all the same.

The cost is transition complexity. Every remap is a rebalance period with
overlapping owners. The churn repeats as often as N changes.

Data pattern: sustained uniform overload, where static capacity steps arrive
too slowly.

### 5. Static capacity

Add partitions and consumers, with N fixed at each deployment.

This is not a correction. It is capacity. It is the honest first answer when
every partition is deep, and it needs no new mechanism. Its cost is
operational, not technical.

Data pattern: all partitions deep, waits uniform across partitions.

## The measurement, landed now

Nothing persisted queue wait before this card. `intake.enqueued_at` dies with
the ack. The run row carried no timestamps. Phase 2 could not have produced
the data this decision needs.

`db/005_run_timing.sql` adds three columns to `run`:

- `enqueued_at`: the arrival time, copied from the intake row at pickup. It
  survives the ack. It stays null for callers with no queue.
- `created_at`: pickup time. It fills itself through a default, so every
  insert path records it.
- `finished_at`: stamped when a run enters a terminal state, in the same
  transaction as the state change.

Two measures follow. Queue wait is `created_at - enqueued_at`. Service time
is `finished_at - created_at`. The precedent is `approval_edit_distance`
(db/003): a run column added so a Phase 2 measure reads from the ledger
alone.

Per-partition skew follows from the same rows, grouped by `run.partition`.
Little's law converts mean wait into mean queue depth at a known arrival
rate. No depth sampler ships; wait history carries the signal.

The Phase 2 report reads one query:

```sql
SELECT partition,
       count(*) AS runs,
       percentile_disc(0.50) WITHIN GROUP (ORDER BY created_at - enqueued_at) AS wait_p50,
       percentile_disc(0.90) WITHIN GROUP (ORDER BY created_at - enqueued_at) AS wait_p90,
       percentile_disc(0.90) WITHIN GROUP (ORDER BY finished_at - created_at) AS service_p90
FROM run
WHERE enqueued_at IS NOT NULL
  AND finished_at IS NOT NULL
GROUP BY partition
ORDER BY wait_p90 DESC;
```

Two scope notes. V1-era rows keep `enqueued_at` null, and their `created_at`
reads as the migration time; the report filters both away. The proposed
DEC-35 key change moves the partition key to the conversation id. The three
columns ride the run row and stay correct under any key.

## Decision rules for Phase 2

Each rule reads the landed columns. Apply them in order.

- **R1, all partitions deep.** Waits sit high and uniform across partitions.
  This is capacity. Apply option 5 first, then option 4 if deploys lag
  demand.
- **R2, skew.** A few partitions hold most of the wait while others sit
  idle. Apply option 3, or move the partition boundaries at the next deploy.
  A steal needs the per-ticket fence bump, never a bare foreign poll.
- **R3, heavy-tailed service.** Depth is uniform but a few long runs cause
  most of the wait. Apply option 1. Reordering cannot help the
  unprioritized majority.
- **R4, one harmed class.** One class takes disproportionate damage from
  wait. Apply option 2 with an aging term. This rule shapes a tail for one
  class; it removes no delay.

Rules can fire together. Capacity first, then the shape of the residual wait
picks the correction.

| Ownership overlap is fenced | DEC-28, section 4.2 |

| Run columns as the Phase 2 measure | db/003 precedent, section 4.10 |

## Rejected alternatives

- **Ship option 1 now.** It is the cheapest correction. It also multiplies
  the blast radius of every scan before any evidence says the tail causes
  the wait. The register's method runs the measurement first.
- **A lease with a lock service.** DEC-27 rejected it. Section 3.4 shows a
  lease without fencing does not close the gap.
- **Priority by age.** That is arrival order, the current behaviour, under a
  different name.
- **A queue-depth sampler.** Depth follows from wait through Little's law.
  A sampler adds a moving part that carries no new signal.
- **Auto-scaling N from live depth.** A feedback loop over shared queue
  state can oscillate. It also needs the same wait data first, so it cannot
  leapfrog the measurement.

## Open items

- Who owns the Phase 2 latency review. The adopter names the person, as with
  open item 1.
- The concurrency bound K for option 1, if rule R3 fires.
- The aging parameters for option 2 and the steal threshold for option 3.
- Whether option 1 needs a register note. One consumer working several
  tickets at once changes no guarantee in DEC-27's text. A person confirms
  this reading, or the register gains a clarifying sentence.
